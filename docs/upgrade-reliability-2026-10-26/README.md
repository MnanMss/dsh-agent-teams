# 升级可靠性：单变量实验与最小改造

## 问题与不变量

目标是减少我们自己造成的版本维护遗漏，不承诺未知官方 API 自动兼容。基线为 main `43a3f160e20a1f316ca32340b3676aae7d7d4b82`。本次没有修改生产 `src/`、构建产物、支持版本集合、推荐版本或开发依赖；保持 FIFO、角色/工具权限、失败传播、冷恢复、精确版本与依赖身份保护。

升级是否成功取决于三个独立事实：宿主行为是否兼容、插件产物是否声明该宿主、用户实际安装的发布包是否包含该声明。CI 验收还必须经过用户使用的安装入口，不能只绕过安装器直接链接插件。

## 消融与对照

| 候选机制 | 单变量实验 | 行为证据 | 成本/取舍 |
| --- | --- | --- | --- |
| 只对 rc.2/rc.3 运行安装探针、要求安装证据 | 给旧 CI 汇总代码输入假想 rc.999 的完整生命周期报告，但不提供安装报告 | 旧逻辑输出通过；仅删除 lifecycle 报告则拒绝，排除整个汇总未执行的解释 | 删除版本特判；新候选默认要求安装探针 |
| YAML 中单独维护 Windows 版本列表 | 新增一个假想支持目标，不修改 workflow | 新计划自动产生 Ubuntu/Windows 两项；缺任一报告均拒绝 | 矩阵执行和汇总共用一份策略；旧 13 项覆盖保留 |
| 手动同步 21 份相同 peer 范围 | 只增加支持清单，不改 package.json；随后运行生成器 | 修前校验拒绝；生成后全部声明一致；未知版本仍不在范围，混装/缺 peer 仍被拒 | 一个显式生成命令替代手改 21 个范围；发布字段仍保留，不删除保护 |
| 放宽 engines.dsh 以消除拒装 | 仅加入 `engines.dsh: "*"`，调用官方 rc.3 发布产物的 evaluatePluginCompatibility，目标是假想 rc.999 | 精确声明返回 21 个 mismatch，宽 engines 直接通过；没有任何运行兼容证据 | 拒绝该替代方案；补上校验器对 engines 优先级的检查 |
| 仅以 main/package.version 判断交付完成 | 保持插件版本号相同，将 registry manifest 的 rc.3 声明移除 | 状态检查仍识别未交付支持；真实 npm 查询复现同样结果 | 增加只读声明差距检查，不自动批准或发布 |

假想 rc.999 / 0.3.0 是测试输入，不代表真实发布、兼容或 API 迁移证据。[基线结果](baseline.json) 包含原汇总输出和官方安装门禁消融结果。

## 实现与旧路径退役

- `compatibility.json` 是版本和平台覆盖策略来源。历史 fixture-only 目标显式记录限制；其余默认运行真实安装。
- `harness-validation.mjs` 生成目标并校验报告。workflow 原内联汇总代码已删除，runner 原 rc.2/rc.3 数组已删除，不保留双轨验收。
- `pnpm sync:compatibility` 显式派生 peer 声明；未改变清单时不会重写文件。普通检查不自动修正源码，缺失声明不会被静默掩盖。
- `pnpm check:upstream` 查询宿主 latest/next 与插件 latest，分开报告未验证上游与未交付支持。网络错误、缺渠道、缺声明或宽范围不会显示全绿。该命令没有自动定时触发，不覆盖其他 tag/未标记版本。
- 原运行时适配层保留：当前没有实验支持删除其跨代 FIFO、初始化、权限或恢复分支。把公开 sendMessage 当作 FIFO 的替代也未获证明，本次不改。

维护操作见 [维护流程](../maintenance-workflow.md)。平台例外和历史安装限制不能在添加新宿主时机械复制，需要明确审查。

## 验证与边界

1. `pnpm install --frozen-lockfile`、全套 `pnpm verify` 通过；修改后定向测试覆盖声明生成、未知版本、混装、缺失 peer、engines 覆盖、缺安装场景、错误摘要/平台/插件版本、缺报告及 registry 错误。
2. 使用新汇总器重读已归档的 13 份 CI 报告，全数通过。它证明旧验收范围保留，不是本次重新运行了 13 个宿主。
3. [本次真实运行结果](runtime-rc3.json)：macOS arm64、Node 26.7、DSH rc.3（296 个同代包）运行安装、生命周期与冷恢复，包含忙时 FIFO、队员权限和推理力度断言，全部通过。模型为 fixture，用户 profile 未修改；不代表真实 provider、浏览器或原生 Desktop 验证。
4. 独立审查发现本次测试写死目标总数、缺 next 标签可能全绿；已修复。审查者在隔离副本新增 0.3.0、生成 peers 后重跑 23 项测试通过，缺 next 的纯逻辑与 fetch 入口均拒绝。
5. [Registry 实查](registry-status.json)：官方 latest=rc.2、next=rc.3；插件 latest=0.1.26 缺 rc.3 声明。源码同版本号不代表 npm 包已更新。该结果按采集时间解释，本任务没有发布 npm。

本次未测量性能、内存或模型费用变化，不宣称此类收益。确定减少的是重复版本名单与手动声明同步；新增检查在维护/CI 阶段执行，不增加产品模型调用。未来宿主发生真实接口改变时，仍须按精确版本审计并迁移。
